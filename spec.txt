1. Executive Summary
IRMS (Internal Resource Management System) is a centralized SaaS platform for managing employees, operational sites, coordinators, projects, daily timesheets, vehicles, accommodation, rooms and room inventory. The MVP is designed to replace fragmented paper records, spreadsheets and informal operational tracking with a structured, searchable and auditable system.
* Centralized employee master records and supporting documents.
* Site and coordinator management across multiple operational locations.
* Project creation and employee-to-project assignment with historical records.
* Daily site timesheet submission, attachment and approval workflow.
* Vehicle master data and employee/site/project assignment history.
* Accommodation, room allocation and room inventory tracking.
* Management dashboard, reports, notifications and audit logs.
* Multi-tenant SaaS architecture with role-based access control and tenant isolation.
2. Product Positioning
POSITIONING STATEMENT
IRMS gives organizations one operational source of truth for who is working where, on which project, under which coordinator, using which vehicle, staying in which accommodation/room, and what daily work record has been submitted.
	

3. Source Business Requirement
The source requirement describes an organization with approximately 1,300 staff, 23 sites, 5 coordinators and 50 vehicles. The required system is described as a basic operational system for employee details, daily site timesheets, coordinator/site relationships, vehicle assignment, accommodation/room records, room contents and project assignments.

6. Operational Modules & Procedures
6.1 Employee Management
Employee record should support identification, employment, contact and operational assignment information.
* Employee ID / Employee Number
* Full name, nationality, gender and date of birth
* National ID / Passport number
* Profile photo
* Joining date, job title, department, position and employment type
* Supervisor and coordinator
* Current site and project
* Mobile, email and emergency contact
* Assigned vehicle and accommodation/room
* Active / inactive / leave / transferred / terminated / suspended status
1. Authorized user opens Employees and selects Add Employee.
2. System validates mandatory fields and employee-number uniqueness within the tenant.
3. Employee is saved with an audit record.
4. User may upload documents and create operational assignments.
5. System maintains historical assignments instead of overwriting prior records.
6.2 Employee Documents
* Document categories must be configurable.
* Store document metadata in PostgreSQL and files in private object storage.
* Support issue/expiry dates and status calculation.
* Provide 7/30/60/90-day expiry visibility.
* Downloads must use authorization checks and short-lived signed URLs.
6.3 Sites & Coordinators
* Site code, name, description, address, city/region, GPS coordinates and status.
* Primary coordinator and future support for multiple coordinator assignments.
* Site-to-project relationships.
* Site operational dashboard showing employees, projects, vehicles and timesheet status.
6. Create site.
7. Assign coordinator.
8. Associate one or more projects.
9. Assign employees and operational resources through controlled assignment records.
6.4 Projects & Employee Assignments
* Project code, name, client, description, dates, manager/coordinator and status.
* Project-site relationship.
* Employee assignment records with role, start date, end date and status.
* Historical assignments must remain available after transfers.
6.5 Daily Timesheets
10. Coordinator selects Site and Date.
11. System loads employees assigned to the selected operational scope.
12. Coordinator records Present, Absent, Leave or Off.
13. Optional check-in, check-out, regular hours, overtime and notes are captured.
14. Supporting timesheet PDF/JPG/PNG/XLSX may be attached.
15. Record is saved as Draft or submitted.
16. Approver reviews and approves or rejects.
17. Approved records become controlled; post-approval changes require an authorized edit request and reason.
6.6 Fleet / Vehicles
* Registration/plate, make, model, year, VIN, type and current mileage.
* Insurance, registration and inspection expiry dates.
* Vehicle status: Available, Assigned, Maintenance, Out of Service or Sold.
* Assignment records must capture employee, site, project, start and return dates.
* System must prevent conflicting active vehicle assignments.
6.7 Accommodation & Room Inventory
* Accommodation facility → building → floor → room hierarchy.
* Room capacity and occupancy status.
* Employee room/bed assignment with check-in/check-out dates.
* Room inventory with item, category, quantity, condition and notes.
* System must warn or reject capacity violations according to configuration.

9. API & Backend Standards
* Version APIs under /api/v1.
* Validate every request server-side.
* Enforce tenant ownership and permissions on every protected resource.
* Use consistent success/error response structures.
* Use pagination for list endpoints.
* Use database transactions for multi-record critical operations.
* Never expose internal stack traces, secrets or private file paths.
* Create audit entries for important mutations.
Suggested resource groups: /auth, /organizations, /users, /employees, /sites, /coordinators, /projects, /assignments, /timesheets, /vehicles, /accommodations, /rooms, /inventory, /reports, /notifications, /audit-logs, /settings.
10. Security & Compliance Baseline
* Strict tenant isolation.
* RBAC enforced server-side; UI visibility is not a security boundary.
* Password hashing using a modern password hashing algorithm.
* HTTPS in all production environments.
* Secure cookies/tokens, session expiry and logout invalidation.
* Rate limiting and brute-force protection.
* Input validation, output encoding and injection protection.
* Private document storage with signed temporary download URLs.
* Security headers and secure CORS configuration.
* Immutable audit logging for sensitive operations.
* Secrets supplied through environment/secret management, never committed to source control.

12. SaaS / Multi-Tenant Requirements
* Each organization is an isolated tenant.
* Every business record carries an organization/tenant reference.
* Organization users cannot access another organization's data.
* Support organization-level settings and configurable statuses.
* SaaS admin can manage organizations, users, usage and system health.
* Billing/subscription architecture may be prepared for future activation without expanding the MVP scope.
13. Data Migration & Import
18. User uploads CSV/XLSX.
19. System validates structure and mandatory fields.
20. System provides a preview before commit.
21. Validation errors are displayed per row/field.
22. User confirms import.
23. Valid records are committed transactionally where practical.
24. Import result reports created, updated, skipped and failed records.
25. Import action is audited.

17. MVP Acceptance Criteria
